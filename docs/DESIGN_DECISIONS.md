# 设计决策文档（面试准备稿）

> 本文回答"为什么这么设计"。每个决策都按「问题 → 备选方案 → 决策与理由 → 残余风险」展开，
> 目标是面试中能脱稿讲清每一层的取舍，而不是复述"我做了什么"。

## 1. 项目定位：为什么是"沙箱引擎"而不是"数据分析网页"

**问题**：2023 年起"上传 Excel → AI 分析"的套壳产品已经泛滥，2026 年通用聊天客户端原生就
能做。这个项目的功能价值不成立。

**决策**：把可复用的核心资产——*安全执行 LLM 生成代码 + 量化其可靠性*——独立为
`analyzer/` 引擎包（零 UI 依赖），Streamlit 降级为演示壳，另提供 CLI 无界面入口。

**理由**：
- 产品会过时，问题不会。"企业数据不能出域、生成代码不能裸跑、输出质量必须可度量"
  是 2026 年企业落地 LLM 的真实约束，正好对应本项目的三个模块：脱敏、沙箱、评测。
- 引擎/壳分离让"界面可替换"成为可演示的事实：同一个引擎，网页和 `python -m analyzer`
  两条入口。

## 2. 沙箱：为什么 AST 校验 + 子进程，而不是 Docker

**威胁模型（先答这个）**：本机单用户工具，模型生成的代码不可信。要防的不是国家级攻击者，
而是三类现实风险：模型幻觉产生的破坏性代码（误删文件、死循环）、提示注入诱导的越权行为、
以及最平凡的——合法但昂贵的计算把应用卡死。

**分层防御**：
1. **静态层（AST 白名单）**：禁 import/while/def/class/try，禁 os/sys/socket 等标识符，
   禁 dunder 属性访问，pandas/NumPy 只开放白名单方法（所有 read_*、to_* 文件接口不可达）。
   校验执行两次：父进程先验（快速失败，省一次进程创建），子进程再验（纵深防御——
   子进程永远不信任父进程"已经查过了"）。
2. **动态层（子进程隔离）**：代码在一次性子进程里执行，带硬超时（默认 20s）和内存看门狗
   （默认 1024MB）。失控进程被杀，主应用无感。

**为什么不用 Docker**：Windows 单机工具引入 Docker 是部署负担倒挂——用户是"双击 bat
的小白"（见一键部署脚本），为防自己机器上的幻觉代码装 Docker 不成比例。子进程 + 资源
上限对这个威胁模型已经足够，且零依赖。

**为什么不 pickle 结果回传**：子进程执行过不可信代码，它的输出就是不可信数据。
pickle 反序列化可执行构造数据，是经典注入面。所以父→子用 pickle（父产生的可信载荷），
子→父只回传 JSON。**信任边界不对称**是整个协议的核心一条。

### 实测挖出的潜伏 bug（好故事，值得讲）

第一版看门狗盯着"直接子进程"的 RSS，内存测试永远不触发。诊断发现 Windows 下 venv 的
`python.exe` 是 5MB 的启动器壳，真解释器是它的**子进程**——看门狗量的是壳，kill 也只杀壳，
真解释器会变成孤儿继续跑失控代码。修复为按进程树监控内存、按进程树击杀（psutil 递归
children）。这条链路（测试失败 → 观测 RSS → 假设 → 验证 → 修复）本身就是工程能力的证据。

### 残余风险（如实说，面试官追问时不要装完美）

- AST 看不见字符串内部：`"{0.__class__}".format(df)` 这类 format-string 属性遍历能绕过
  dunder 拦截。当前不承诺抵御一切解释器逃逸——隔离边界是"进程可杀 + 输出不反序列化"，
  即使逃逸也拿不到持久化能力。彻底方案是 Pyodide/WASM 或容器级隔离，属于 roadmap。
- 无网络层封锁：靠命名空间（无 import、socket 不可达）阻断，不是防火墙级保证。
- 大文件场景：DataFrame 经 pickle 进子进程，内存翻倍；分块读取在 roadmap 里。

## 3. 评测：口径定义

- **一轮成功率**：`attempts == 1` 且判分通过——模型"一次写对"的能力。
- **最终成功率**：重试预算（2 次自动纠错）内判分通过——产品实际交付的能力。
- **收敛分布**：按成功时的 attempts 统计，反映自动纠错的价值。
- **P50/P95 延迟**：每题完整链路墙钟时间（含全部重试与沙箱开销）。
- **判分哲学**：验"数值正确"，不苛求表达——value_close 在相对误差内找匹配单元格；
  frame_equal 按行多重集比对（列名不敏感、顺序不敏感），另设显式降序校验。
  列名是 UX 问题，不是正确性问题。
- **黄金答案不硬编码**：每题的 reference 代码在运行时数据上现算，数据生成器种子固定，
  杜绝"数据变了答案没变"的漂移。
- **口径陷阱类**：折扣率/单价等比率列求 sum 是典型业务口径错误（prompt 里专门约束
  "比率用 mean"），这类题衡量的是业务口径 sense，不只是代码能力。

### 首轮真实评测的发现（glm-4-flash，2026-09-13）

一轮 15/18 = 83.3%，P50 16.4s，全程零超时零拦截。三道失败全部是**理解层**问题：
两道复合双问句（"哪个城市？销量多少？"）模型只答一半，返回 1×1 而非 1×2；一道
"单日销售额最高"被算成单笔口径。结论：执行层（生成→沙箱→归一化）已经稳定，
下一轮迭代方向是问句分解或澄清追问，而不是继续加固执行层——评测的价值正在于
把"该改哪里"从感觉变成证据。

另外一个判分器自身的教训：引擎会把 permuted unnamed index 作为 "index" 列暴露，
而模型答案往往没有这列——判分器最初被这个表现层伪影骗过（形状不一致），修复为
双方先剥掉纯行号标记列再比对。判分器也要评测，这是元层面的同一课。

## 4. 依赖取舍：为什么删 LangChain

LangChain 全家桶（4 包 + dashscope SDK 共 6 包）只有 dashscope 一条分支在用，而
DashScope 本身提供 OpenAI 兼容端点——整套依赖换来的能力是零。代码里还有四层
try/except TypeError 降级补丁，意味着三条未测试的失败路径。

决策：四家 provider 统一走 OpenAI SDK + 各自 base_url，一个客户端构造路径。直接依赖
15 → 13（requirements.txt 现存 13 项），`llm_service` 324 → 284 行。**保留了 kaleido**（PNG 图表导出唯一依赖）——
砍掉会让现有功能静默降级，依赖瘦身不等于无脑砍。

另修一个部署真 bug：`.deps_ok` 空文件哨兵导致 requirements 变更后不重装依赖，
哨兵改为记录清单 SHA256。

## 5. 其他值得 30 秒讲清的决策

- **脱敏的双层设计**：输入侧（profile 只发列名/类型/聚合统计，不发原始行）+
  输出侧（导出文件转义 `=`/`+`/`@`/`-` 前缀，防 CSV/Excel 公式注入，OWASP CSV Injection）。
  一个防"数据出去"，一个防"危险进来"，合起来才是完整的数据安全叙事。
- **聚合口径进 prompt**：金额求和、比率求平均——这是业务 sense，不是代码能力；
  评测集里专门放了"口径陷阱"类来度量它。
- **结果归一化的 index 语义**：有名字/多层的 index 保留为列（是分组键），默认
  RangeIndex 丢弃（是行号）——LLM 生成 groupby 代码的展示质量由此决定。
- **表头自动探测**：Excel 透视表上面有标题行导致 Unnamed 列名，按"非 Unnamed 列数"
  打分探测表头行——来自真实实习场景（BOM 单据解析）的迁移。

## 6. 面试追问预案（自测）

1. 沙箱防谁？→ 讲威胁模型三分类（幻觉/注入/DoS），再讲分层。
2. `"{0.__class__}".format(df)` 能绕过你的检查吗？→ 能，AST 看不见字符串内部；
   讲残余风险边界和 roadmap。
3. 为什么不用 Docker？→ 部署负担倒挂 + 威胁模型不成比例。
4. 怎么证明你的沙箱有效？→ 超时/内存/拒绝路径的单元测试 + 评测集的
   timeout/memory/reject 计数。
5. 代码生成成功率多少？怎么定义？→ 一轮 vs 最终，收敛分布，看 eval_report.md。
6. 为什么删 LangChain？→ 能力为零 + 失败路径；但 kaleido 保留了，说明不是无脑砍。
7. 和 PandasAI / Code Interpreter 的区别？→ 本地不出域（数据安全）+ 可复用引擎
   （两个入口）+ 有自己的评测（质量度量）。
